# レビューから学ぶ注意点まとめ

国内15件・海外200件のPac-Manレビュー（[reviews_pac-man.md](reviews_pac-man.md)、[reviews_pac-man_oversea.md](reviews_pac-man_oversea.md)）から、
**落ちた理由**と**減点・指摘されたポイント**を抜き出し、課題文（[ja.subject.pdf](../../ja.subject.pdf)）の要件と照らし合わせてまとめた。

> 結論：0点になったチームのほとんどは「よくできているけど、要件の細部を1つ落とした」パターン。
> 評価者はチェックリストを1行ずつ確認し、**評価中に config.json を書き換えて壊しにくる**。
> 0点・減点の原因は、ゲームの出来ではなく、細部の要件漏れとエラー処理であることが多い。

## 1. 実際に0点・減点になった理由

| 結果 | 原因 | 該当する要件 |
|---|---|---|
| 0点 Crash | `highscore_filename` 周りの小さなミスでクラッシュ | V.2 / V.5、クラッシュ厳禁 |
| 0点 Incomplete | config.json / highscore.json の `name` のパースエラー | V.3 不正な設定への対処、V.5 名前の検証 |
| 0点 Incomplete | **MLXに同等の関数がない関数を使用**（forbidden function） | 第IV章 MLX同等ライブラリ |
| 0点 Incomplete | config の `pacgum` の得点設定が反映されていなかった | V.2、VI.6 得点 |
| 0点 Ok | 迷路生成パッケージのバージョン不一致で `uv` がエラー（自動で解決すべき） | V.4、Makefile install |
| 0点 Incomplete | **レベルが10未満** | VI.7 レベルは最低10 |
| 0点 Ok | メインメニューに操作説明がない ＋ **最初のレベル以外もseedが固定**されたまま | VI.1 seedは最初だけ固定 |
| 0点 Incomplete group | メンバーが1人欠席 | 評価には全員そろって参加 |
| 96点 | README の小さなミス | 第IX章 README |
| 95点 | エラー処理の小さな漏れ | V.1 / V.3 |
| 100点だが指摘 | パッケージ生成が課題・評価シートの要求どおりではなかった | 第VII章 パッケージ化 |
| 100点だが指摘 | README の AI 使用欄がない | 第IX章 Resources |

## 2. 気をつけることチェックリスト

### 2-1. 設定ファイル（評価中に必ず壊される）
- [ ] `#` で始まる行をコメントとして扱える
- [ ] キーが不足している／値が不正（型違い、負の数、空文字、巨大な値）なら**既定値に補正し、ログを出して続行**する
- [ ] 不明なキーは無視する
- [ ] ファイルがない、JSONが壊れている、引数がない、引数が2つ以上ある、拡張子が `.json` でない場合も、トレースバックを出さずにメッセージを出す
- [ ] `points_per_pacgum` などの**得点設定が実際に反映される**か確認する（反映漏れで0点になった例あり）
- [ ] 迷路サイズの上限・下限を決めておく（「20x20より大きい迷路を扱えるようにするか制限すべき」という指摘あり）
- [ ] 評価者は「configが壊れなかった」ことを高く評価している → 意地悪な入力をまとめたテスト用configを用意しておく

### 2-2. ハイスコア
- [ ] `highscore_filename` の値がおかしい（存在しないディレクトリ、書き込み権限がない、空文字）場合でも落ちない
- [ ] ハイスコアファイルが壊れている／中身が不正な形式でも落ちない
- [ ] 名前は**最大10文字・英数字とスペースのみ**。入力時と**読み込み時の両方**で検証する（読み込み時のパースエラーで0点になった例あり）
- [ ] 得点は非負の整数のみ。上位10件だけ保持する
- [ ] 勝っても負けても名前を入力でき、メインメニューに表示される

### 2-3. ゲーム仕様の細部
- [ ] **レベルは10以上**
- [ ] **最初のレベルだけ固定seed**、2レベル目以降はランダム（全部固定で0点になった例あり）
- [ ] スーパーパックガムは4隅、ゴーストは4体で各隅に1体、プレイヤーは中央から開始
- [ ] スーパーパックガムも含めて食べ切らないとクリアにならない（「super pacgumでのレベルクリアに注意」という指摘あり）
- [ ] 各レベルに制限時間があり、時間切れの動作を決めて README に書く
- [ ] 一時停止と再開ができる
- [ ] 得点と残機はレベルをまたいで引き継ぐ
- [ ] **メインメニューに操作説明を表示する**（ないことが減点理由の1つになった）

### 2-4. グラフィックライブラリ（MLX同等）
- [ ] 使うpygameの関数が**MLXに同等品があるものだけ**か確認する（ウィンドウ、画像表示、ピクセル描画、文字列表示、キー入力、ループフック）
- [ ] 「使用関数とMLXの対応表」を管理資料に残し、評価時に見せられるようにする（forbidden functionで0点になった例あり）
- [ ] 高評価のチームは、pygameを**MLX風のラッパークラス**で包んでいた → 使える関数が限られていることを構造で示せる

### 2-5. チートモード
- [ ] 無敵・レベルスキップ・ゴースト停止・残機追加・速度上昇をそろえる（評価者は全項目をチートで確認する）
- [ ] **チートの使い方を README やゲーム内に書く**（「cheat modeの説明を追加して」という指摘あり）
- [ ] 残機追加をくり返すなどのストレステストで表示が崩れないか確認する

### 2-6. 迷路生成パッケージ・環境構築
- [ ] 割り当てられたA-Maze-ingパッケージは**変更せずに使う**（評価中に再インストールされる）
- [ ] バージョン指定と `uv` の lock がずれないようにする。`make install` だけで環境が完成するようにする（バージョンエラーで0点になった例あり）
  - 今のこのプロジェクトは `pyproject.toml` でローカルの whl をパス指定しているので、別の環境でクリーンにインストールして動くか確認する
- [ ] 生成器が失敗した場合も適切に処理する

### 2-7. パッケージ化・配布（itch.io など）
- [ ] 公開プラットフォームから**ダウンロードして単体で動く**ことを、別の環境で確認する
- [ ] パッケージ内に操作・オプション・設定の説明を入れる
- [ ] リポジトリのルートにパッケージ作成用のスクリプトや仕様を置き、評価中に**作り直せる**ようにしておく
- [ ] itch.io のページに画像を入れる（「itchに画像がない」という指摘あり）
- [ ] Web版を出すなら、デスクトップ版との違いに注意する

### 2-8. コード品質・Makefile
- [ ] `make lint`（`flake8 .` と `mypy . --warn-return-any`）が通る（高評価のレビューで言及されている）
- [ ] すべての関数に型ヒントと docstring（PEP 257）を付ける
- [ ] `install` / `run` / `debug` / `clean` / `lint` のルールを用意する
- [ ] 実行中のライブラリのログは消しておき、ターミナルをきれいにする（PyRayのログについて指摘あり）
- [ ] `make run` 中に Ctrl+Z を押してから再度 `make run` すると、前のウィンドウが固まる問題が指摘された → シグナル処理を考えておく

### 2-9. README（英語）
- [ ] 1行目はイタリックで `This project has been created as part of the 42 curriculum by ...`
- [ ] Description / Instructions / Resources（**AIの使い方を必ず書く**）
- [ ] Configuration / Highscore / Maze Generation / Implementation / General Software Architecture / Project Management の各節
- [ ] READMEの小さなミスで96点になった例あり → 提出前に要件と1項目ずつ照らし合わせる

### 2-10. 評価当日
- [ ] **メンバー全員が参加する**（欠席で0点になった例あり）
- [ ] 両方のメンバーが、自分の担当だけでなく全体のコードを説明できるようにしておく
- [ ] クラス図などの**図を用意しておく**と説明が伝わりやすい（指摘あり）
- [ ] 設計の判断理由（なぜ継承／なぜ共通化しなかったか、ECSかOOPか など）を説明できるようにしておく。OOPの議論になりやすい
- [ ] Git履歴、カンバン、作業記録などのプロジェクト管理の証拠を見せられるようにしておく
- [ ] 操作に注意する：終了キーが複数あったり、WASDのすぐ近くの `q` で即終了したりすると誤操作が起きる

## 3. 高評価（Outstanding）になったポイント

- 自作の素材・音楽（BGMやタイトル曲）など、細部へのこだわり
- ゴーストごとに違う追跡ロジック（Blinky/Pinky/Inky/Clyde風）と、状態遷移
- 設計の明快さ：config / ロジック / 描画 / ハイスコアの分離、迷路生成器を**アダプター**でつなぐ、ECS や MLXラッパー
- 「壊れないconfig」と、エラー処理のしっかりした作り
- READMEとプロジェクト管理資料が読みやすい（GIF埋め込み、作業記録の可視化）
- 評価者に役立つチート機能

> ただし、Outstandingでも要件を1つ落とせば0点になる（0点 Outstanding project の例あり）。
> **こだわりより先に、まず要件をすべて満たすこと**。
