## 1. 課題の全体像

### 1.1 作るもの

Python 3.10+ で作る、**完成していて遊べる Pac-Man ライクなゲーム**。ゲームだけでなく、次の 4 つが評価対象になる。

| 区分 | 内容 |
|---|---|
| ゲーム本体 | 迷路・プレイヤー・ゴースト 4 体・パックガム・スーパーパックガム・10 レベル以上・制限時間・一時停止・チート |
| 周辺システム | コメント付き JSON の設定ファイル、永続的なハイスコア（上位 10 件） |
| 配布 | itch.io などで**実際にインストールして起動できる**ビルド＋生成スクリプト |
| ドキュメント | 英語の README（指定セクション多数）、プロジェクト管理資料一式 |

起動方法は `python3 pac-man.py config.json` 固定（引数は 1 つだけ）。

### 1.2 ゲームループ（必須の画面遷移）

```
メインメニュー ──▶ ゲーム（HUD 表示） ──▶ 勝利 / ゲームオーバー画面
   ▲  │  │  │           │  ▲                     │
   │  │  │  └─ 終了       ▼  │                     ▼
   │  │  └─ 遊び方     一時停止メニュー       名前入力（最大 10 文字）
   │  └─ ハイスコア       │（再開 / メニューへ）     │
   └──────────────────────┴───────────────────────┘
```

### 1.3 必須要件チェックリスト

**共通ルール（第 III 章）**

- [ ] 未処理例外で落ちたら「機能していない」扱い → **どこで何が起きてもトレースバックを出さない**
- [ ] Makefile：`install` / `run` / `debug` / `clean` / `lint`（任意で `lint-strict`）
- [ ] `.gitignore`、テスト（pytest。採点対象外だが推奨）

**設定ファイル（V.2, V.3）**
- [ ] 標準 JSON ＋ `#` で始まる行をコメントとして無視

- [ ] ファイルがない・JSON が壊れている → 明確なメッセージ（トレースバックなし）

**迷路（V.4, VI.1）**
- [ ] 割り当てパッケージを**改変せず**そのまま使う（レビュー時に再インストールされる）
- [ ] `perfect=False`
- [ ] レベル 1 は固定シード（例：42）、以降はランダム
- [ ] 生成失敗時のエラー処理

**ゲーム仕様（VI 章）**
- [ ] 矢印キー / WASD で 4 方向移動、壁は通れない
- [ ] 残機 3、被弾で中央から復活、0 でゲームオーバー
- [ ] 4 隅にスーパーパックガム、4 隅にゴースト 1 体ずつ、プレイヤーは中央開始

- [ ] レベル 10 以上、各レベルに制限時間、得点・残機は引き継ぎ

- [ ] 一時停止メニュー、勝利画面、ゲームオーバー画面、名前入力

**配布（VII 章）**

- [ ] パッケージ内に操作・オプション・設定の説明
- [ ] リポジトリのルートにパッケージ生成スクリプト（**評価中に再生成を求められることがある**）

**README（IX 章、英語）**

- [ ] Description / Instructions / Resources（AI の使い方も記載）

## 2. 割り当てられた迷路パッケージ（mazegenerator 2.1.0）の要点

`mazegenerator-00001.zip` の中身を実際に読んだ結果。**ローダーは相手のインターフェースに合わせる**（パッケージ側は直せない）ので、癖を最初に把握しておく。

```python
from mazegenerator import MazeGenerator

gen = MazeGenerator(size=(width, height), perfect=False, seed=42)
grid = gen.maze          # list[list[int]]、grid[y][x]
```

| 項目 | 内容 | 注意点 |
|---|---|---|
| コンストラクタ | `MazeGenerator(size=(w, h), perfect, entry_cell, exit_cell, seed)` | **同梱 README の Quick Start（`width=`, `height=`）は間違い**。実際は `size=(w, h)` |
| データ形式 | `maze[y][x]` の int。下位 4bit が壁 | N=1, E=2, S=4, W=8。ビットが立っていると**壁あり** |
| 座標 | `maze_entry` などは `(x, y)` | README には `(row, col)` とあるがコードは `(x, y)` |
| `seed=0` | 完全ランダム | レベル 2 以降はこれでよい |
| 中央の「42」 | 値 15（四方が壁）の孤立セル群が中央に入る | **パックガムを置かない・ゴーストやプレイヤーを置かない**。中央開始なので「中央に一番近い通行可能セル」を探す処理が必要 |
| 小さい迷路 | 幅 14 未満 or 高さ 10 未満だと「42」を入れず `print` で警告 | 標準出力に勝手に文字が出る |
| 乱数 | `random.seed()` で**グローバル乱数を書き換える** | ゴーストの AI などでグローバル `random` を使うと再現性が壊れる → ゲーム側は `random.Random()` のインスタンスを使う |
| `perfect=False` | 行き止まりを除去する（Pac-Man 向け） | 課題要件どおり必ず False |

設計上の判断：迷路は「セルとセルの間に壁がある」形式。Pac-Man でよくある「マス自体が壁か通路か」の形式とは違う。
**ロジックはこのセル形式のまま扱う**（隣のセルに移動できるかは壁ビットを見るだけでよい）のが一番単純でおすすめ。描画のときだけ壁を線として描く。

## 3. どこに時間がかかるか

### 3.1 工数の見積もり（相対値）

| # | 作業 | 重さ | 理由 |
|---|---|---|---|
| 1 | **移動と当たり判定の手触り** | ★★★★★ | マス単位の論理と、なめらかな描画（補間）の両立。先行入力（曲がり角の手前でキーを押しておく）、すれ違い時の当たり抜け（プレイヤーとゴーストが同じフレームで位置を入れ替えると衝突を見逃す）。ここの品質が「洗練された UI」の印象を決める |
| 2 | **ゴーストの状態管理と AI** | ★★★★☆ | 追跡 / いじけ / 食べられた / 復活待ちの状態遷移、タイマー、逃走ロジック、ゴースト同士の重なり。BFS で追跡するのが確実 |
| 3 | **配布（PyInstaller ＋ itch.io）** | ★★★★☆ | 未知要素が一番多い。外部 wheel・画像・フォント・既定の設定ファイルの同梱、ハイスコアの書き込み先（パッケージ内は書き込めないことがある）、Linux 以外での動作。**最初の週に技術検証を済ませる** |
| 4 | **画面遷移と UI 一式** | ★★★☆☆ | メニュー・遊び方・ハイスコア・一時停止・勝利 / ゲームオーバー・名前入力（文字種と長さの制限）。1 つずつは簡単だが数が多い |
| 5 | **堅牢性（クラッシュ禁止）＋ mypy / flake8** | ★★★☆☆ | 設定の全パターンの不正値、ハイスコアファイルの破損、迷路生成失敗、画像読み込み失敗。後からまとめてやると地獄なので**最初から型を付けて lint を通し続ける** |
| 6 | **ドキュメント（README ＋ 管理資料）** | ★★★☆☆ | 要求セクションが多い。プロジェクト管理の「証拠」は後から作れないので、**毎週少しずつ記録する** |
| 7 | 設定ファイル・ハイスコア | ★★☆☆☆ | 処理自体は単純。テストを書きやすいので pytest で固める |
| 8 | 迷路の読み込み | ★☆☆☆☆ | 上記の癖さえ押さえれば小さい |

### 3.2 早めに決めておかないと後で困ること

1. **グラフィックライブラリ**：課題は「MLX と同等の関数だけ使える」という制約付き。
   pygame を使う場合も、使う関数が MLX に同等品のあるもの（ウィンドウ、画像の表示、ピクセル描画、文字列表示、キー入力、ループフック）に限られる。
   - MLX に音声機能はないので、**サウンドは使えない**と考えておくのが安全
   - 円や線の描画関数（`pygame.draw.*`）が許されるかは解釈が分かれる → **スプライト画像を表示する方式**にしておけば安全
   - 使ってよい範囲は**周りのグループやスタッフにも確認**して、判断と理由を管理資料に残す
2. **ゲームの更新方式**：固定時間ステップ（例：60 Hz で論理を更新）にする。フレームレートに速度が左右される実装は後から直しにくい。
3. **制限時間切れのときの動作**：自由。おすすめは「残機を 1 減らしてレベルをやり直す」（シンプルで説明しやすい）。
4. **ハイスコアの保存場所**：開発時はプロジェクト内、配布ビルドではユーザーのホームディレクトリ（例：`~/.pacman/highscores.json`）。設定の `highscore_filename` で変えられるようにする。

## 4. 役割分担（2 人）

並行で作業できるように、**「ゲームの中身（ロジック）」と「外側（表示・入出力・配布）」**で分ける。境界は「描画側はゲーム状態を読むだけで、書き換えない」こと。

### Aさん：ゲームロジック担当

| 担当 | 中身 |
|---|---|
| 迷路アダプタ | `MazeGenerator` を包み、自前の `Maze` クラス（通行判定・隣接セル・中央セル・4 隅）に変換 |
| エンティティ | `Player`、`Ghost`（状態遷移・AI）、移動と当たり判定 |
| レベル進行 | パックガム配置、得点、残機、制限時間、レベル遷移、勝敗判定 |
| チート | 無敵・スキップ・停止・残機追加・速度アップのロジック側 |
| テスト | ロジックの単体テスト（描画なしで動くように作る） |

### Bさん：表示・システム担当

| 担当 | 中身 |
|---|---|
| 設定 | コメント付き JSON の読み込み、検証、既定値への補正、ログ |
| ハイスコア | 読み込み・保存・上位 10 件管理・名前の検証 |
| 描画と入力 | ウィンドウ、スプライト、迷路の描画、HUD、キー入力をゲームへの命令に変換 |
| 画面遷移 | メニュー・遊び方・ハイスコア・一時停止・勝利 / ゲームオーバー・名前入力 |
| 配布 | PyInstaller の設定、itch.io への公開、生成スクリプト |
| 環境 | Makefile、`.gitignore`、エントリポイント `pac-man.py` |

### 2 人で一緒にやること

- **初日にインターフェースを決める**：`GameState` に何を持たせるか、入力をどう渡すか（下の 5 章）。ここが決まれば別々に作れる。
- **README とプロジェクト管理資料**：自分の担当部分は自分で書き、全体はどちらかがまとめる。
- **相互レビュー**：相手のコードは必ずレビューしてからマージする。評価では「ランダムな箇所の改造」を求められるので、**2 人とも全体を説明できる状態**にしておくのが必須（Bさんがゴースト AI を、Aさんが設定読み込みを説明できるように）。
- 週 1 回の振り返り：進捗を計画と比べ、ズレと対策を管理資料に記録する。

> 分担は負担が偏らないよう 2 週目の終わりに見直す。配布で詰まった場合は Aさんも手伝う、など。

## 5. 想定アーキテクチャ（たたき台）

```
PacMan/
├── pac-man.py                # エントリポイント（引数チェック → App 起動）
├── config.json               # 既定の設定（コメント付き）
├── Makefile
├── README.md
├── build/                    # パッケージ生成スクリプト・spec（Bさん）
├── assets/                   # スプライト・フォント
├── pacman/
│   ├── config.py             # Config（dataclass）＋ 読み込み・検証（Bさん）
│   ├── highscore.py          # HighscoreTable（Bさん）
│   ├── maze.py               # Maze：mazegenerator のアダプタ（Aさん）
│   ├── entities.py           # Player, Ghost, GhostState（Aさん）
│   ├── game.py               # GameState / Level：1 ステップ分の更新処理（Aさん）
│   ├── cheats.py             # チート（Aさん）
│   ├── render.py             # 描画（Bさん）
│   ├── input.py              # キー入力 → Command（Bさん）
│   └── screens/              # Menu, HowTo, Highscores, Playing, Pause, GameOver, Victory, NameEntry（Bさん）
├── tests/
└── project_management/       # この資料・スケジュール・リスク・テスト計画など
```

**A と B の境界（初日に合意する部分）**

```python
class Game:
    def handle(self, command: Command) -> None: ...   # B → A：入力（UP/DOWN/LEFT/RIGHT/PAUSE/CHEAT_*）
    def update(self, dt: float) -> None: ...          # 固定ステップで呼ぶ
    @property
    def state(self) -> GameState: ...                 # A → B：描画用の読み取り専用データ
```

`GameState` には迷路、プレイヤーとゴーストの位置・向き・状態、残りのパックガム、得点、残機、レベル、残り時間、終了状態（続行中 / 勝利 / 敗北）を持たせる。

## 7. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ライブラリの関数が「MLX 同等でない」と判断される | 評価で不合格 | 使う関数の一覧と MLX の対応表を作り、根拠を管理資料に残す |
| 配布ビルドが他の環境で起動しない | 必須要件未達 | 1 週目に技術検証、別のマシンでもインストールして確認 |
| 評価中の設定変更でクラッシュ | 「機能していない」扱い | 不正値のパターンを列挙して pytest で網羅。`main` の最外周でも例外を捕まえてメッセージ表示 |
| 迷路サイズによって中央・隅が想定どおりにならない | 開始位置不正・到達不能 | 「最寄りの通行可能セル」を探す処理を入れ、サイズ範囲を設定の検証で制限 |
| 迷路パッケージがグローバル乱数を書き換える | ゴーストの動きが再現できない | ゲーム側は独自の `random.Random` インスタンスを使う |
| 一方しか理解していないコードがある | 評価で説明できない | マージ前の相互レビュー必須、4 週目に模擬評価 |
| 最後に lint エラーが大量に出る | 終盤の時間を圧迫 | コミット前に `make lint` を通すことをルールにする |
| AI 生成コードを理解しないまま使う | 評価で説明できず不合格（課題 II 章） | AI の出力は必ず相手と一緒に読み、使った箇所と使い方を README の Resources に記録 |

## 8. 作業ルール（提案）

- ブランチ：`main` は常に動く状態。作業は `feature/<内容>` ブランチ → PR → 相手がレビュー → マージ。
- コミット前に `make lint` とテストを通す。
- タスク管理：GitHub Projects などのカンバン（ToDo / Doing / Review / Done）。スクリーンショットを週 1 回 `project_management/` に保存すると「計画と実績の比較」の証拠になる。
- 判断したことは `project_management/decisions.md` に 1 行ずつ記録（ライブラリ選定、制限時間切れの挙動、ハイスコア保存場所など）。README の各セクションと評価時の説明にそのまま使える。
- 問題やもめごとが起きたら `project_management/issues_log.md` に記録（課題で「障害や対立の概要」を求められている）。

## 9. 最初にやること

1. 2 人でこの資料を読み合わせ、分担とスケジュールの期間を確定する
2. グラフィックライブラリを決める（使える関数の範囲も合わせて）
3. `Game` / `GameState` / `Command` のインターフェースを決めてコードの雛形を作る
4. Makefile・`.gitignore`・`pyproject.toml`（または `requirements.txt`）・venv を準備し、wheel をインストールして迷路を 1 つ表示してみる
5. Bさんは並行して「Hello World を PyInstaller でビルドして itch.io に置き、別のマシンで起動する」まで試す
